# Lockfile policy (`package-lock.json` / `npm-shrinkwrap.json`)

## Status of this checkout

`package-lock.json` **is present and committed** in this directory. It was generated by a
real `npm install` against the public registry on the pinned toolchain
(Node v22.18.0 / npm 10.9.3), so every `integrity` value in it is a genuine sha512 from
the registry.

`npm-shrinkwrap.json` is **not** used: the gateway is a private, deployed application,
not a published package, so `package-lock.json` is the correct lock file.

## Never hand-write a lockfile

Do not create or edit `package-lock.json` (or any `integrity:` value) by hand to make a
build "work". A fabricated hash either fails `npm ci` with `EINTEGRITY`, or — worse —
pins a tarball nobody verified. If the lock file is missing, generate it:

```cmd
cd agents\aragon-gateway
npm install --no-audit --no-fund --include=dev
```

## The `NODE_ENV=production` trap

This workstation has `NODE_ENV=production` exported globally. In that state:

- `npm install` silently installs **no** devDependencies (`typescript`, `tsx`, `vitest`
  are missing afterwards) and still reports success / "up to date";
- `npx tsc` then fails with "could not determine executable".

Always pass `--include=dev` when installing for development or CI typechecking. The
Dockerfile sets `NODE_ENV=development` explicitly in its build stage for the same reason,
and uses `npm ci --omit=dev` only in the runtime stage.

## Regenerating after an engine upgrade

`POST /internal/admin/reload {target_version}` switches the *running* engine child without
touching this file. Committing a new pin is a separate, deliberate step:

```cmd
npm install @aragon-agent/core@<version> --save-exact --no-audit --no-fund
npm run typecheck
npx vitest run          :: conformance suite must be green, or the upgrade is blocked
```

Then update `ENGINE_PIN`, the `package.json` entry and `README.md`'s pin table together —
the tool reports the version it actually imports, so a mismatch shows up in `/healthz`
rather than being hidden.
